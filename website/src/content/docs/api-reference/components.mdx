jEngine registers 179 components. A scene, a prefab or a script's spawn names one by its **scene key** - the `"components"` object of an entity is keyed by it. Every component is plain data and reads and writes as JSON; a field left out takes its default.

80 of them belong to an **engine feature**: an optional subsystem a game's build carries only when its project uses it. The builder finds the features a project uses from its assets - a component key in a scene or prefab is one of the signs - so naming one of these components is enough. A component made only by a script, from a key assembled at run time, is a sign the builder cannot see: list its feature under `include` in the project's `settings.engine_features`. A component whose feature column is empty is in every build.

Packages register components of their own; those are on each [package's page](/packages/).

### camera

**Type:** `Camera2DComponent` · **Editor:** Camera 2D · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

Camera component — marks an entity as a game camera.

Multiple cameras can exist: the active one with no `target` and the highest `priority` draws the screen (`ecs::camera_rig::main_camera`), and one taking over from another can `blend`. Requires a `Transform` on the same entity.

| Field | Type | Description |
|-------|------|-------------|
| `zoom` | `f32` | Zoom level (1.0 = default). Higher values zoom in. |
| `is_active` | `bool` | Whether this camera is the currently active (rendering) camera. |
| `viewport_width` | `f32` | Viewport width hint (overridden at runtime by actual window size). |
| `viewport_height` | `f32` | Viewport height hint (overridden at runtime by actual window size). |
| `stretch` | `bool` | Stretch `viewport_width` x `viewport_height` over a screen of another shape, instead of showing more world along the longer axis (`Camera2D::fit_view`). Off by default: stretched, a square is drawn wide on a phone. |
| `pixel_size` | `f32` | Draw the world at one pixel per `pixel_size` world units and scale it up - pixel art at its own resolution, on its own grid, scrolling smoothly (`renderer::pixel_perfect`). 0, the default, draws at the screen's resolution. Script: `Camera.set_pixel_size`. |
| `integer_scale` | `bool` | With `pixel_size`, draw every art pixel as a whole number of screen pixels, showing a little more world to fill the screen (`Camera2D::integer_view`). Off by default: the authored area fills the screen exactly and an art pixel may be 4.27 screen pixels wide. |
| `target` | `String` | Draw into a texture of this name instead of onto the screen: a **view** (`ecs::views`). Any sprite, mesh or UI image naming it as its `texture_id` shows what this camera sees - a monitor, a minimap, one half of a split screen. Empty, the default, is the main camera. |
| `target_size` | `[u32; 2]` | The target texture's size in pixels; 0 takes the screen's. |
| `cull_mask` | `u32` | Which render layers this camera draws (a bitmask against each entity's `render_layers`, layer 1 for one with none). All of them by default - Unity's culling mask, Godot's cull mask: a minimap that shows markers the street views do not. |
| `screen_rect` | `[f32; 4]` | Draw onto this part of the screen (Oct 2026; Unity's viewport rect): `[x, y, w, h]` as fractions of the screen from its top-left, y down - `[0, 0, 0.5, 1]` is the left half. The camera becomes a view drawing into a texture of its share's size, shown by an image beneath every other UI (`ecs::views::sync_screen_rects`) - split screen with no target or UI to author. All zero, the default, is none. |
| `priority` | `i32` | Which active camera draws the screen (Oct 2026; Cinemachine's priority): the highest, the first of them on a tie. Raise one to hand it the view - `Camera.set(e, "priority", 10)`. |

| `confine` | `Vec<[f32; 2]>` | A polygon, in world units, this camera's **view** stays inside - every edge of the screen, not only its centre (Cinemachine's confiner): a gallery of any shape whose walls the view never looks past (`ecs::camera_rig::confine`). Empty, the default, is none. |

### prefab_instance

**Type:** `PrefabInstance` · **Editor:** Prefab Instance · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

Marks an entity as an instance of a named prefab template.

2.2 — Prefab variants / overrides. Authored in a scene as `"prefab_instance": { "prefab_id": "Player", "overrides": { ... } }`. At scene-load time, `scene::prefab::expand_prefab_instances` looks the template up in the runtime's prefab map, merges its components onto the entity (any components the scene already authored win over the template), then applies dotted-path overrides on top.

The component is retained on the spawned entity as a marker so scripts / tooling can ask "what prefab did this come from?".

**A prefab can carry one too** (Oct 2026): it is then a *variant* of the prefab it names - the base, its own components over it, then these overrides (`scene::prefab::resolve_prefab_variants`, which every runtime runs on its prefab map) - so a family of creatures is one prefab and its differences, and a variant of a variant works.

| Field | Type | Description |

| `overrides` | `HashMap<String, serde_json::Value>` | Per-instance property overrides keyed by dotted path (e.g. `"sprite.color"`, `"transform.position"`, or a top-level component key like `"sprite"` to replace the whole component). Values are raw `serde_json::Value`s applied via `serde_json::Value::pointer_mut`-style traversal. |

### mesh

**Type:** `Mesh2D` · **Editor:** Mesh · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

A textured polygon: what a sprite is, with the corners free.

Drawn **in the sprite pass**, sorted with the sprites, shadows and world text by `z_order`, batched with sprites of the same texture, and put through the entity's `MaterialComponent` like a sprite. That is the difference from `VectorPath` (flat colour, its own pass, always over every sprite) and from `SkinnedMesh` (needs a skeleton, its own pass), and it is why a mesh can be a wall in a first-person corridor with a monster sprite standing in front of it. `SpriteComponent::corners` is the four-vertex, one-colour, affine-textured special case of this.

Nothing in the engine writes the vertices: a package or a script does, per frame if it likes. That is the point - a corridor's walls, a flag in the wind and a jelly are all "a system that writes a `Mesh2D`".

A mesh is never a backdrop: it is not drawn beneath the tilemaps however low its z, because the tilemap pass draws sprites only.

### trail

**Type:** `Trail` · **Editor:** Trail · **Engine feature:** `trails` · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

A **trail**: a ribbon left behind the entity as it moves - a sword's swing, a comet's tail, a light painted with the mouse. Unity's `TrailRenderer`, Godot's `Line2D` fed from a script.

Every frame of play the entity's world position is recorded once it has moved `min_distance` from the last point (`ecs::trails::tick_trails`, which every runtime runs right after resolving the hierarchy); a point lives `lifetime` seconds. `Trail.set_emitting` and `Trail.clear` steer it from a script. Long gaps between points - a fast swing - are drawn as curves, not chords. The ribbon runs from the entity's position this frame back through the points, its width and colour going from `width` / `color` at the head to `width_end` / `color_end` at a point's last moment - so with a `color_end` of alpha 0 or a `width_end` of 0 a point fades out rather than popping off the tail. The texture is stretched along the whole ribbon: `u` 0 at the head and 1 at the tail, `v` across.

Drawn in the sprite pass (sorted by `z_order` with sprites, lit unless `Unlit`, blended by `blend_mode`). A trail on a child is the trail of where the child is - put one on the tip of a sword, not the hilt.

|-------|------|-------------|
| `lifetime` | `f32` | How long a point lives, in seconds - the length of the tail in time. |
| `width` | `f32` | Width at the head, in world units. |
| `width_end` | `f32` | Width at a point's last moment. |
| `color` | `[f32; 4]` | Colour (linear RGBA) at the head. |
| `color_end` | `[f32; 4]` | Colour at a point's last moment. |
| `min_distance` | `f32` | How far the entity moves before a new point is recorded. Smaller is smoother and costs more points (at most `Trail::MAX_POINTS`). |
| `texture_id` | `String` | Texture stretched along the ribbon; empty is plain colour. |
| `z_order` | `i32` |  |

### unlit

**Type:** `Unlit` · **Editor:** Unlit · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

Marker: this entity's sprite and text ignore 2D lighting.

World-space sprites and text are drawn into the scene target and then multiplied by the light buffer, so in a dark scene a label is as dark as the floor it sits on - that is right for a sign painted on a wall, and wrong for a caption explaining the scene. An `Unlit` entity is drawn after the lighting composite instead, at full brightness.

Unlit things sort with lit ones by `z_order` (since Sep 2026): the world pass draws an unlit sprite as a cutout in the lit scene and as itself in an emission buffer the composite adds after the light, so it is full brightness *and* hidden by a lit sprite in front of it. They used to be drawn after all lit content, above it whatever the z - a lit window on a far tower showed through the building in front. ### ambient_occlusion

**Type:** `AmbientOcclusion` · **Editor:** Ambient Occlusion · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

**Ambient occlusion**: the ambient light darkened near the outlines of `LightOccluder`s, as it is where two surfaces meet - the soft darkening at the foot of a wall, in a corner, between two boxes set close. Put it on any one entity (the first found is used), beside the `ambient_light`.

A point `d` from an occluder's outline keeps `1 - strength * (1 - d/radius)^2` of the ambient light from that occluder, and nothing within `radius` of none; near two occluders the two multiply, so a corner or a narrow gap goes darker than one wall. A point *inside* an occluder takes none from that occluder - the top of a box is not darkened by its own sides. Only the ambient term is occluded: a lamp still lights a corner. Godot builds the same thing from its occluders' distance field; the showcase's Clay scene is built on it. `renderer::lighting::ambient_occlusion_at` is the rule, on the CPU and (transcribed) on the GPU.

| Field | Type | Description |
|-------|------|-------------|
| `radius` | `f32` | How far from an outline the darkening reaches, in world units. |
| `strength` | `f32` | How dark it gets at the outline itself: 0 none, 1 black. |

### directional_light

**Type:** `DirectionalLight2D` · **Editor:** Directional Light 2D · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

A light from far away - the sun, the moon: every ray parallel, the same strength everywhere, and every shadow thrown the same way. Godot's `DirectionalLight2D`.

Before Sep 2026 a sun was a point light placed thousands of units off screen (the showcase's Clay), whose shadows still fanned out a little across the view, and whose shadows could not lengthen as it set. This is that, done by the engine: `renderer::lighting::sun_as_point` puts the light far out along its direction, beyond the view, so every consumer of point lights - the GPU pass, the occluder packing, `light_at` - handles it unchanged.

A sun is swung by turning its entity (as a spot light is aimed), and set by lowering `height`: shadows lengthen as it does.

| Field | Type | Description |
|-------|------|-------------|
| `color` | `[f32; 3]` | Light color (RGB). |
| `intensity` | `f32` | Light brightness multiplier. |
| `direction` | `f32` | Which way the light travels, in radians (`0` is towards +x, `-PI/2` straight down the screen, the default). The entity's rotation is added. |
| `height` | `f32` | How high the sun stands: the tangent of its elevation, `1` at 45 degrees. It lights normal maps as a point light's `height` does, and it sets how long shadows are - an occluder's `shadow_length` is the shadow it throws under a sun at height `1`, and a sun at `h` throws it `shadow_length / h` long. Occluders with no `shadow_length` cast shadows to the edge of the view at any height. Clamped to at least `0.02`. |
| `softness` | `f32` | The sun's apparent size, in radians: how soft the edges of its shadows are, widening with distance from the occluder. `0` is hard. |
| `casts_shadows` | `bool` | Whether occluders shadow this light. |
| `light_mask` | `u32` | The light layers it lights (Oct 2026; Godot's `range_item_cull_mask`, Unity's target sorting layers): a sprite is lit by the sun when the sprite's `light_layers` shares a bit with this. Every layer by default. Eight layers, the low eight bits. |

### global_illumination

**Type:** `GlobalIllumination` · **Editor:** Global Illumination · **Engine feature:** `gi` · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

**Global illumination** (Oct 2026): light that bounces. The lit outlines of the occluders - the scene's colour times the direct light on them - shine again, and every pixel gathers what reaches it round the occluders between, tinted by what it came off: sun through red glass onto a stone floor warms the walls beside it. Radiance cascades, on the GPU (`renderer::backend::wgpu::gi`), added to the light buffer before the composite. Godot and Unity have no 2D equivalent built in. One per scene, like ambient occlusion; `Lighting.set_global_illumination` sets it. `light_at` leaves bounced light out.

| Field | Type | Description |
|-------|------|-------------|
| `strength` | `f32` | How much of the bounce is added: 1 is what reaches each pixel. |
| `scale` | `u32` | Frame pixels to a GI texel each way: the bounce is soft, so it is worked out small. 4 by default; 2 is finer and four times the work. |
| `cascades` | `u32` | How many cascades - each reaches four times as far as the last. 0, the default, takes as many as cross the frame. |

### light_layers

**Type:** `LightLayers` · **Editor:** Light Layers · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

### light_occluder

**Type:** `LightOccluder` · **Editor:** Light Occluder · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

Marks an entity as a light blocker. During the lighting pass each occluder contributes world-space edge segments that point and spot lights ray-test against — fragments whose line-of-sight to a light is crossed by any segment receive no (or, with soft shadows, reduced) contribution from that light, producing cast shadows / field-of-view wedges.

Shape resolution priority (highest first): 1. `polygon` — an explicit local-space polygon (CCW, closed automatically). Each consecutive pair of points is one edge. 2. `from_alpha` — the silhouette of the sprite's opaque pixels, traced from its texture (`ecs::alpha_shape`); its box until the pixels load. 3. `from_sprite` — derive an axis-aligned box from the entity's `SpriteComponent` size (or its explicit `size` override). 4. `size` — a plain box `size` world units wide/tall.

All shapes are transformed by the entity's `Transform` (position + rotation + scale).

| Field | Type | Description |
|-------|------|-------------|
| `enabled` | `bool` | When false the occluder is ignored (casts no shadow). |
| `size` | `[f32; 2]` | Full width/height of the blocking box in world units, before the entity's `Transform.scale` is applied. Used when neither `polygon` nor `from_sprite` apply. |
| `from_sprite` | `bool` | Derive the blocking box from the entity's `SpriteComponent` bounds instead of `size`. |
| `polygon` | `Vec<[f32; 2]>` | Explicit local-space polygon outline (CCW). Overrides `size` / `from_sprite` when non-empty. Needs at least 3 points. |
| `shadow_tint` | `[f32; 3]` | RGB colour the shadow lets through when `shadow_opacity` is high. `[0, 0, 0]` (the default) produces a neutral shadow; a coloured tint like `[1, 0, 0]` makes a translucent occluder pass only the red channel, simulating coloured glass. |
| `shadow_opacity` | `f32` | How opaque the occluder is in `[0, 1]`. `1.0` (default) fully blocks light (tinted by `shadow_tint`); `0.0` casts no shadow at all; values in between produce translucent shadows. The light passing through equals `mix([1,1,1], shadow_tint, shadow_opacity)`. |
| `self_shadow` | `bool` | Whether the occluder shadows **its own inside** - what Unity calls `ShadowCaster2D.selfShadows`. Off (the default since Sep 2026), a point inside the outline takes light as if the occluder were not there, while everything beyond it is shadowed as before - so a lit wall, pillar or crate that casts a shadow is lit itself, and its normal map shades it. |
| `shadows_casters` | `bool` | Whether its shadow falls on other **casters** - sprites whose entity has an occluder too. On (the default) is top-down lighting, where a wall shadows the crate beside it. Off is a side view (Sep 2026): a tower's blocks stand in front of the wall behind them, so each casts onto the wall and not onto the blocks beside it - with it on, every stone was in its neighbours' shadow and the tower drew black. The GPU knows a caster's pixels from the normal pass; `light_at` has no pixels and treats every point as not a caster. |
| `shadow_length` | `f32` | How far the shadow reaches past the occluder, in world units; `0` (the default) is unbounded. The last quarter fades out. |
| `from_alpha` | `bool` | Cast the **shape of the sprite** (Oct 2026): the outline of its opaque pixels, traced from the texture - a tree's crown and trunk, a fence's pickets - rather than its box. Each island of the sprite is a loop; holes are left out. |
| `alpha_cutoff` | `f32` | The alpha above which a pixel is part of the shape (0..1). |
| `alpha_tolerance` | `f32` | How far, in texels, the traced outline may stray from the pixels' edge - larger is fewer corners. Every corner is an edge each nearby light spends from its pool of 448, so a loop is also held to 48. |
| `traced` | `Option<crate::ecs::alpha_shape::TracedShape>` | The traced outline, kept until the sprite's texture, region, size or anchor change (`ecs::alpha_shape::trace_occluder_shapes`). Never saved. |

### toon_lighting

**Type:** `ToonLighting` · **Editor:** Toon Lighting · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

**Toon lighting**: the light that reaches each pixel is stepped into `bands` levels instead of falling off smoothly - cel shading. A normal-mapped sphere under one light shows a lit face, a mid band and a shadow band with crisp edges between them, as an anime or comic render does. Put it on any one entity (the first found is used).

Applied in the lighting composite to the light buffer - ambient, lights and lightmaps summed - by its brightest channel, so a light's colour is kept. `light_at` applies the same rule (`renderer::lighting::toon_step`).

Each point goes to its **nearest** band, so light under half a band - an ambient below `1 / (2 * bands)` - is black: hard cel shadows. For a lit shadow band, keep the ambient above that (0.17 for three bands).

| Field | Type | Description |
|-------|------|-------------|
| `bands` | `u32` | How many steps light takes between dark and full (at 1.0). Above 1.0 in an HDR scene the steps continue. |
| `softness` | `f32` | How soft the edge between two bands is, as a fraction of a band: `0` is a hard line, `1` is smooth again. |
| `dither` | `f32` | Dithered lighting: the size of a dither cell in **world units**, `0` for none. The `softness` of each band's edge is then drawn as an ordered (4x4 Bayer) pattern of the two bands instead of a gradient - the look of a palette-limited retro game, whose light could only come in a few shades. Anchored to the world, so a cell the size of an art pixel stays on that pixel as the camera moves (and lands on the `pixelate` grid when both use it). |

### ik_two_bone

**Type:** `IkTwoBone` · **Editor:** IK Two Bone · **Engine feature:** `ik` · **Defined in:** `crates/jengine-core/src/animation/ik.rs`

Slice 3.5.F — two-bone IK constraint attached to the *end* (effector) bone of a 3-bone chain `root → mid → end`. The solver walks `Parent` twice from the entity carrying this component to find the `mid` and `root` bones, then rotates `root.Transform.rotation` and `mid.Transform.rotation` (in local space) so that the chain's tip reaches `target` (world-space). Bone lengths come from the `Bone` component's `length` field.

`flip_bend` selects the "elbow up" vs "elbow down" solution.

Scaled and mirrored rigs work (Sep 2026, BUGS #152): the lengths are scaled by each bone's world `scale.x`, and under a mirrored parent (`scale.x * scale.y < 0`, the usual way a 2D character turns round) `flip_bend` keeps its meaning on screen - the knee goes to the mirrored side, as the rest of the character does.

A walk authored on flat ground walks up a slope; the body is the game's to raise.

### despawn_offscreen

**Type:** `DespawnOffscreen` · **Editor:** Despawn Offscreen · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

Despawn this entity once it has left the view.

Every scrolling game needs this and, until Sep 2026, every one of them wrote it again in Lua: walk your own list of spawned things, compare each one against the camera, despawn the ones behind. `Lifetime` covers "this goes away after a while"; this covers "this goes away once nobody can see it", which is the other half.

|-------|------|-------------|

Transient additive jitter offset applied to `Transform.position` for `duration` seconds. Intensity decays linearly from `intensity` at start to `0` at end. Auto-removes itself when expired and restores the entity to its pre-shake position.

Canonical use: hit-reaction camera shake or impact-frame entity shake. The shake is sampled at `frequency` Hz with linear interpolation between samples so the motion stays jittery rather than a smooth sine.

Pure: mutates only `Transform.position`, and only by the jitter: each tick removes last tick's offset and adds a new one, so whatever else moves the entity keeps moving it. When the shake ends the offset is removed.

| Field | Type | Description |
|-------|------|-------------|
| `intensity` | `f32` | Peak displacement magnitude in world units at start. |
| `frequency` | `f32` | New random offset samples per second. |
| `duration` | `f32` | Total shake duration in seconds. |
| `elapsed` | `f32` | Time elapsed inside this shake. Initialise to `0.0`. |
| `offset` | `Option<[f32; 2]>` | Offset applied on the last tick, removed before the next is applied. Runtime state; `None` until the first tick. |
| `seed` | `Option<u32>` | Internal PRNG state seeded on first tick — kept on the component so each entity has its own deterministic stream. |

## Performance

### bulk_entity

**Type:** `BulkEntity` · **Editor:** Bulk Entity · **Defined in:** `crates/jengine-core/src/ecs/components.rs`

Marks an entity spawned in bulk by a system, rather than authored or individually meaningful.

Three things skip it, for the same reason — nobody addresses it one at a time:

1. **The per-frame script mirror.** The browser-script hosts copy every entity's transform into JS each frame so a script *could* call `get_position(e)`. Marked entities are left out. 2. **The editor's Scene panel.** The panel renders one DOM row per entity with several event handlers, and it does not virtualise — 16,000 boids meant ~16,000 rows and roughly 68 ms a frame of layout, against 24 ms of actual engine work. A list that long is useless to a human anyway.

3. **Scene snapshots.** `push_scene` / `pop_scene` and the start of a play session serialize the whole world, and that cost is a hitch mid-game rather than something a save dialog pays. Marked entities are left out by `crate::scene::snapshot_scene_v2`: they belong to a spawner that recreates them, so writing 16,000 boids into a snapshot preserves state nobody addressed individually. Measured at 16,000: **40.05 ms -> 0.35 ms**. A real *save* still keeps every entity — dropping one there would be data loss.

Put it on flocks, projectiles, debris — anything a system creates by the thousand. Simulation and rendering are completely unaffected.

The trade is exact: a marked entity's slot in the script mirror is never filled, so `get_position(e)` reads the zeroed default rather than its real transform; it cannot be selected in the editor; and it does not survive a scene push. If you need to read, move or inspect an entity individually — or to have it come back after a `pop_scene` — do not mark it.

(Named `NoScriptSync` when first added; renamed once it also governed editor visibility, since the old name described only a third of what it does.)
