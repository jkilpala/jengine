# jengine-server: known limits

The running list of what the server stack does **not** do, or does and has
not been proved to. Written down as each is found, to be sorted out later.

**How to use it.** Add an entry when you find or create a limit - in the same
change, not afterwards. When one is closed, move it to "Closed" at the bottom
with the commit, rather than deleting it: the list is also the record of what
was once true. Each entry says what the limit is, what it costs, and what
closing it would take.

Last gone through: 2026-10-22 (twenty-two times) - every open limit worked
through for 0.1.0: the ones code could close are under "Closed" with the
commit and the test that proves each; what stays open says why, and what a
user has to do about it.

**Changed defaults in this pass** (the README says each where it matters):
`/stats` and `/metrics` want the admin token (`Server::public_stats` opens
them); a password and the admin token are refused when they crossed a
network in plain text (`Server::allow_plain_passwords`,
`Server::admin_over_plain`); an agent listening beyond loopback needs a
release key or `--allow-unsigned`; a host's console refuses its token over
a plain network unless `--allow-plain-console`; cluster calls are signed,
so every node and the coordinator must be upgraded together.

## Not verified

Things that are written and may well work, and have never been run where it
matters. None of these can be closed by more code: they need hardware, a
network or a person.

## Server framework

| # | Limit | What it costs | To close it |
|---|---|---|---|
| S6 | **Prediction is movement.** Steering is predicted and reconciled against walls (`jengine-netcode`, `TileMotion` over `Walls`); a rewound hit is held to the player's measured lag since 2026-10-22 (closed part, below). Still: the tile model is a square avatar in square cells (no slopes, circles or one-way); a custom `Motion` is Rust both ends link; nothing but movement is predicted (no predicted shots, pickups or spawns, so no rollback of them); walls cross the wire whole on every change (no delta); monsters are shown a tick late with no extrapolation. Open: each is a feature not yet written. | A platformer needs its own `Motion`; a big map that changes resends all of itself. | A `Motion` with slopes and one-way platforms; a delta of the walls; predicted events with a confirm-or-undo frame. |
| S7 | **Still JSON text.** Movement goes as `[id, x, y]` triples, but it is text, uncompressed. Open, and not small: compression cannot be negotiated by the native client (tungstenite has no permessage-deflate), so it would be a binary encoding - a protocol change in the server, in `jengine-online` on every runtime, and in any client a game wrote itself. | Bandwidth is a crowded zone's first limit (V4). | A binary `sync` encoding behind a `hello` flag, decoded in `jengine-online`. |
| S11 | **A held seat has edges, by design.** (The one real loss here - a hand-back in flight when the connection died - is closed, below.) A guest - who never said `hello` - gets no grace: there is no token to come back with. The relay kind holds no seats, to stay `jengine-relay`'s protocol. A held seat is a taken seat: a full room stays full for `grace` seconds. | A room that wants its seats back sooner sets a shorter grace. | Deliberate; nothing to close. |
| S12 | **A channel's members are per node.** Joining says who is in it, moderators can list channels, mute a player in one and clear its backlog across the cluster (closed part, below) - but a member connected to another node is heard and not listed. | Who is in a channel looks smaller than it is on a cluster. | Presence through the coordinator. |
| S25 | **State shared by every room of a kind has no home.** An MMO's parties, a village's shared building project and its mail live in an `Arc<Mutex<..>>` captured by the room factory, the durable part backed by the `Store`. One process is one world: a cluster's rooms on two nodes each have their own copy, and in-memory groups do not survive a restart. Open: it needs the coordinator to hold shared objects, which it does not. | Fine on one machine; wrong on a cluster. | Keep what must be shared in the `Store` (a key per group), or run such a game on one node. A kind-level shared object held by the coordinator would close it. |
| S29 | **New (2026-10-22): a node and its coordinator must agree on the time** within five minutes, and on the protocol: cluster calls are signed with a timestamp, and the bearer secret is no longer taken. | A node whose clock drifts is refused (it says "are the clocks set?" in the coordinator's log); an old node cannot talk to a new coordinator. | Run NTP on every machine; upgrade a cluster's nodes and coordinator together. |
| S30 | **New (2026-10-22): a store that writes behind can lose its last moment.** `Server::write_behind` takes writes at once and sends them a batch at a time; a process killed outright loses what it had not sent (a clean stop and every hand-over to another node flush first). Off by default. | Milliseconds of saves on a crash. | Use it for a store a network away, where the round trip costs more than the window risks. |

## Cluster (several nodes, one world)

| # | Limit | What it costs | To close it |
|---|---|---|---|
| K1 | **The coordinator is one process, with no standby.** It can stop and come back - players on play on, sign-ins are refused with the reason, writes wait on the nodes and go out on its return, a new coordinator is told what each node holds. But while it is down nobody signs in, changes node or claims a room; a node that dies then takes its waiting writes with it. Waiting writes are deliberately **not** spooled to disk: replayed after a crash they could overwrite a newer save made on another node meanwhile (there is no version on a record to tell). | An outage is a pause, not data loss - unless a node fails too. | A standby coordinator; versioned records, after which waiting writes can be spooled safely. Meanwhile: run the coordinator on the most reliable machine and back up its database. |
| K3 | **A room is placed once and stays.** Placement weighs players and machine load; a room is never moved. A node that dies loses its rooms' play since the last autosave, and they open empty elsewhere once the coordinator notices (10 s). | Load that builds up inside a room stays. | Handing a room to another node. |
| K4 | **One zone is one node, by design.** The cluster spreads rooms; it does not split one. | One zone is bounded by one machine (V4). | Smaller zones; seamless zones are not planned. |
| K5 | **A redirect is a reconnect.** The client opens a new socket, signs in again and joins: a few hundred milliseconds in no room; channels are rejoined by `jengine-online`, what was said meanwhile is missed. | A blink at a door between machines. | Keep the socket on a gateway and move only the room behind it. |
| K8 | **Not run on separate machines, and the fleet does not know about clusters.** Tested as a coordinator and nodes in one process and as processes on one machine. `jengine-fleet` deploys each as an ordinary service. | Real latency and partitions are unseen; a deploy restarts nodes one by one with no drain of rooms to their neighbours. | A two-machine run (hardware); fleet awareness of roles (code, not yet written). |
