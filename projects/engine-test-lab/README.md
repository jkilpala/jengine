# engine-test-lab

A master QA project that walks every major jEngine feature in a focused
mini-scene. Open it in the editor, run it natively, build it for the web —
each scene must behave identically across all three runtimes.

**[SWEEP.md](SWEEP.md) is the checklist for doing that**: one row per scene
saying what must be true, with a box per runtime. Tick it as you go, so a
scene nobody has re-run since the commit that added it is visible as a scene
nobody has re-run.

## Run natively

```powershell
cd projects/engine-test-lab
cargo run -p jengine-runtime
```

The runtime boots `scenes/hub.scene` (the menu), from which every feature
scene is reachable. While in any scene:

- `Esc` / `Backspace` / `H` — return to hub
- `PageDown` / `]` — next scene in the tour
- `PageUp`   / `[` — previous scene in the tour

In the hub itself the scene list is a scrolling container: the mouse wheel
scrolls it, as do `Up` / `Down`, `PageUp` / `PageDown` and `Home` / `End`.


## Adding a scene — do this for every new engine feature

**Every engine feature gets a scene here.** A feature with no scene in this
project is a feature nobody re-checks after the commit that added it, and this
is the only place where native / editor / web are compared side by side.

Adding one is six edits, all asset-side (no rebuild):

1. `assets/scenes/NN-name.scene` — camera, a `Title` and `Hint` text entity,
   and whatever the feature needs. Copy the nearest existing scene.
2. `assets/scripts/lua/scene_NN_name.lua` — `require("lua/nav")` and call
   `nav.tick(SCENE_PATH)` from `update` so H / Esc / `[` / `]` keep working.
3. `assets/scripts/lua/nav.lua` — append the scene path to `M.TOUR`.
4. `assets/ui/hub.gui` — one more Button node under `scene_list`
   (`btn_scene_NN`). The list scrolls, so length is not a constraint.
5. `assets/scripts/lua/hub.lua` — one more `{ "btn_scene_NN", "scenes/..." }`
   row in `BUTTONS`.
6. `SWEEP.md` — a row saying what to look for, with a box per runtime
   (`every_scene_has_a_sweep_row` fails a scene without one).

Then run it in all three runtimes and log any divergence in
BUGS.md. If the feature is script-facing, it also needs an entry in
[`docs/scripting-api.md`](../../docs/scripting-api.md) and the parity wiring
listed in [`CLAUDE.md`](../../CLAUDE.md).
