# Parity gaps — the register

**Every known place where the four runtimes disagree, and its current status.**

jEngine runs the same game through four execution paths — native (Luau), the
editor viewport (Fengari), the browser preamble (JS), and `jengine-web`
(Fengari) — each with its own registration. Compiling proves nothing about
whether a function exists, and a gap is usually **silent in the runtime you are
not looking at**. This file is where those gaps live so they stop being
rediscovered.

## The rule

> **When a gap is fixed, mark it fixed here in the same change that fixes it.**

Move the row's status to **FIXED**, add the date and what closed it, and keep
the entry. Do not delete it — a closed gap is the most useful thing to read
when the same mistake is about to be made again, and several of these have been
closed and reopened.

A fix is not finished until:

1. The entry below says **FIXED**, dated, naming what closed it.
2. Any machine-checked list that named it has been **updated** — see *Ratchets*
   below. Those tests fail when a listed gap is closed without removing it,
   which is deliberate: it forces this file and the code to agree.
3. The viewport is rebuilt if the fix touched Rust (`./build-viewport.ps1`).

## Two grades of gap

Worth naming, because only the first is caught by `cargo test`:

| Grade | Symptom | Caught by |
|---|---|---|
| **1 — missing name** | `attempt to call a nil value (global 'x')` — loud, one runtime | `script_global_parity` |
| **2 — present but inert** | The name binds, the call returns null, nothing happens — invisible | `node tools/conformance.mjs` (Oct 2026): test-lab scene 224 writes known state and reads it back through every getter it can reach, natively and in a web build, and the tool diffs the answers. Not part of `cargo test` - it needs a window, a browser and a web build - so run it after touching a host or the preamble. |

Grade 2 is the dangerous one. Everything in §2 below is grade 2.

### The order of a frame

| Gap | Where | Status |
|---|---|---|
| **The three hosts tick a frame in different orders** | all | **FIXED 2026-10-10** - in the browsers' order: the world, the physics step, trigger areas and the graph barrier, combat, UI, then the scripts, then the camera; native rearranged to it (its `tick_world` is gone, each step placed in the frame), the editor's barrier moved to after the trigger areas as the web has it, and both browsers poll pads before the input actions that read them (the editor polled only when a script ran, so a scene driven by graphs or components never saw a controller). `frame_order_is_the_same_everywhere`. What it was, found by listing each host's calls into core in order: The same steps, in three orders: **native** runs the scripts *first*, then the world (motion, trigger areas, combat and animation, lifetimes), then UI navigation, the physics step and its contacts, then the behaviour-graph barrier; **the web** runs the world first - motion, the physics step, trigger areas, the graph barrier, combat and animation, UI navigation - and the scripts *last*; **the editor** is the web's order but with the graph barrier *after* combat, animation and the lifetimes. Each is a frame of difference, which is why nothing has visibly broken - and why a game tuned to the frame in one runtime can be a frame off in another. The steps that already agree are shared since Oct 2026 (`tick_combat_and_animation`, `physics_frame_begin` / `_fixed_step` / `_end`, `pose_world_for_draw`, `ecs::frame_draw`); making the *order* one is a decision about which frame a script sees, not a refactor, and it moves behaviour in at least one runtime. |

Found while designing a pseudo-3D road package, by asking what order shapes and sprites draw in - the answer being that on three runtimes they do not draw at all. Same family as BUGS #144 (`apply_physics_commands` had one caller and neither end of the handoff existed): **a missing call is invisible to any test of the function it should have called.** Closed by building a `WgpuShapeBatch` in the native runtime and in `jengine-web` and drawing it at the same point in the frame the viewport does, so all three agree about stacking. Guarded by `cargo test -p jengine-core --test render_passes_reach_every_runtime`, which requires every `pub fn render_*` in `wgpu_systems.rs` to be **classified** - drawn by every runtime, deliberately editor-only, or wired nowhere - and fails on a pass that reaches some runtimes and not others. That guard was itself verified by reintroducing the bug: the first version counted the name inside comments, so commenting the call out still passed. |

Worth noting what this implies for the register itself: the two grades above are
both about *script globals*, and this is neither. A component can be wired
everywhere a component is wired - registry, scene format, save/load - and still
never reach a screen, because rendering it is a separate call that only one
runtime makes. Nothing machine-checked that the four runtimes draw the same set
of components; `render_passes_reach_every_runtime` now does, and a new render
pass has to say which runtimes draw it before the suite will go green.

## 3. Deliberate differences

Not gaps. Listed so nobody "fixes" them.

| Behaviour | Why |
|---|---|
| `quit_game()` is a logged no-op on web | A browser tab cannot close itself. Menus that offer Quit should hide the button on web. |
| `Platform.*` reach a portal only in a web build made for one | Oct 2026 ([web-platforms.md](web-platforms.md)). Natively, in the editor and in a build for no portal there is no portal to tell: the calls do nothing, `Platform.name()` is `"none"` and `show_ad` answers at once through `platform_ad_finished`, not shown - the same answer everywhere, so the ad flow is the same code in every runtime. A portal's pause and mute exist only in the web runtime (`jengine-web/src/platform.rs`); the editor viewport never reads them. Test with a build: test-lab scene 295. |
| Asset packs are always `installed` in the editor (and a native run from the project folder) | Only a build moves a pack's files out of the game, so there is nothing to download: every declared pack is local, `Packs.download` / `remove` do nothing and `Packs.of` answers `""` (no manifest names the files). A built game - native or web - reads `assets/packs.json` and starts each pack `remote`. Test the download flow in a build (test-lab scene 225). |
| The editor's Play asks live ops for the `dev` channel and applies no content release | Deliberate. A built game asks `settings.liveops.channel` (`live`) as its platform and lays the release over its packs; the editor asks `editor_channel` (`dev`) as platform `editor` (`viewport_set_liveops` calls `liveops::web::init(.., true)`), so testers see in-progress values and targeting rules can tell the editor apart. Its packs are the project's own files, so a release is not applied there. Remote config, variants and events behave the same. |
| ~~`SkinnedMesh` draws **over every sprite**, whatever its `z_order`~~ **FIXED 2026-09-24** | It was its own pass after the sprite pass (`render_skinned_meshes_wgpu`), in the same place in every runtime, so `z_order` only ordered it against other skinned meshes. Now skinned on the CPU and drawn inside the interleaved sprite pass as the sprite of its texture, the way `Mesh2D` and `VectorPath` are (golden `skinned_mesh_in_sprite_pass`; `skinned_meshes_are_drawn_by_every_runtime_in_the_sprite_pass` refuses a runtime that still calls the old pass, which would draw every mesh twice). `VectorPath` had the same row, fixed the same day. |
| Batch scripts (`batch_script`, tier 3) run only natively | The worker pool is OS threads, each with a QuickJS runtime, and wasm has neither. In the editor and on the web a `batch_script` entity is loaded and left alone - its drifters sit still - and test-lab scene 58 says so on screen. Porting it would mean a browser JS path for the same `update(ctx, q)` contract, not a fix to this one. |
| Save slots are **per project** natively and **per origin** in a browser | A native game keeps its saves in its own folder; a web build keeps them in `localStorage` as `jengine_save:<slot>`, and every game published on one site is one origin - so two games' slots of the same name are one slot. A game must not assume a slot is its alone on the web: name it after the game, or key what is per-game inside it. Two online game collections on one site met it (Oct 2026): the shared `profile` slot carried one collection's server into the other, which asked that server for a room kind it did not have ("no room kind 'dice'"); their shared `lib/link.lua` now keeps the typed server under the collection's own default and the token under its server. Namespacing web saves by project in the engine would fix every game at once, but strands every save players already have. |
| `dd` (debug-shape passthrough) is viewport-only | It feeds `viewport_get_debug_draws`, which only the editor has. |
| `lds` (editor-driven scene load) is viewport-only | Not emitted by the preamble at all. |
| `require` is absent from `BRIDGE_FUNCTIONS` | Fengari resolves it in Lua against the seeded script cache; there is no command to send. |
| Luau has `math.atan2`; Fengari has 2-arg `math.atan` and no `atan2` | Dialect difference, not a gap. Neither supports both spellings — a game's own `lib/mathx.lua` can probe and fall back. Assume anything deprecated between Lua 5.1 and 5.3 needs the same treatment. **Ratcheted since Sep 2026** in one game collection's own tests (`dialect_only_library_functions_are_probed_before_they_are_called`), which fail on any of its scripts naming `math.atan2` without also testing for it. It exists because a ship-duel game shipped a bare call in its bot: native flew, and in the editor the throw killed the rest of `update` every frame — no HUD, no callouts, a dead pause key — which reads as most of a game being broken rather than as one missing function. |
| `string.format("%d", x)` on a fractional `x`: **Luau truncates, Fengari throws** | Dialect difference and the nastiest shape of one, because the *silent* side is native. Measured Sep 2026: Luau 0.663 gives `37` for `37.99` and `-2` for `-2.5`; Lua 5.3 raises `bad argument #2 to 'format' (number has no integer representation)`, which kills the whole `update` once per frame. Every number a script reads out of a published component arrives as a float, so this is one multiplication away in any game - a lantern game hit it with `brightness * 100` and ran fine on native while being dead in the editor. **Floor it in Lua** (`math.floor(v + 0.5)`) rather than relying on either: that also makes the two runtimes agree, which `%d` itself does not, since Luau truncates where a reader expects rounding. No ratchet catches it - a project guard that compiles scripts does not run them, and one game collection had ~135 unfloored `%d` sites that worked only because their values happened to be whole. |

## 4. Ratchets — what is machine-checked

These tests are the reason the lists above are short. Run them when touching
anything script-facing.

| Test | Guards |
|---|---|
| `script_global_parity` | Native registrations vs. `BRIDGE_FUNCTIONS`. Fails on a **new** gap in either direction, **and** when a listed gap is closed without deleting its entry. |
| `host_command_parity` | Both browser hosts (viewport + web) dispatch the same command tags, and every tag the preamble emits is handled by both. |
| `preamble_command_tags` | No two script globals share a `{ t: '<tag>' }` tag. The namespace is flat and undeclared, so a reused tag is nearly silent — the first `match` arm wins and the older function stops working. Also: every `__jengine_*` name in the preamble is read off `window`, since a bare one is a `ReferenceError` that binds fine and throws on call (BUGS #57). |
| `scripting_conformance` | Luau and the JS host adapter emit an identical command stream for the same fixture. Does not cover the Fengari path - see the next row. |
| `tools/conformance.mjs` (not a cargo test) | Test-lab scene 224 run natively and in Chrome against a web build: ~60 getters answering the same known state, line by line. The browser half is the real web host - its publish and its command arms - which no cargo test can run. Its first run found that a missing entity's position is two nils natively and one on the web (harmless, and normalised). |
| `gui_scroll_reaches_every_runtime` | Every runtime wheel-scrolls and drag-scrolls GUI containers, fires clicks on release, and publishes the gesture to `InputState`. A **source scan**: the failure mode is a runtime that never calls shared code, which compiling cannot see. |
| `entity_ui_reaches_every_runtime` | Every runtime calls `update_ui_widgets`, and the renderer places widgets through the same `UIElement::screen_center` the hit test uses. Before Sep 2026 **no** runtime called its predecessor, so no entity-UI button was clickable anywhere, and the slider, toggle and text input had no interaction code at all (BUGS #61). |
| `ui_scaling_reaches_every_runtime` | Every runtime lays the UI out in virtual pixels, builds its UI projection over the same virtual size, hit-tests with the divided pointer, and converts clip rects back to physical pixels. Doing some but not all of those draws a UI that answers clicks somewhere it is not. |
| `region_frames_reach_every_surface` | Every surface that draws a sprite resolves atlas `region` names - the native runtime, the editor's Scene tab *and* Play mode, and the animation preview. An unresolved region is the **whole texture**, so a missing call looks like bad art rather than a bug (BUGS #83). |
| `post_process_resets_between_scenes` | Every runtime replaces the effect chain when a scene loads, carries it on its scene stack, and (the editor) restores it on Stop - and the scene-block parser stays a single function. A chain that is never replaced follows the player into the next scene (BUGS #84). |
| `lit_sprites_reach_every_runtime` | Every runtime draws normal maps through the deferred normal pass (`render_normals_wgpu`, before the lights; the forward `lit_sprite` pass is gone since Sep 2026), loads their normal maps, resolves textures through the shared `lit_sprite_textures`, never uploads a normal map as sRGB colour, draws `Unlit` things into the emission buffer *before* the composite reads it (since Sep 2026, in z order with lit ones), and UI and GUI *after* it so world lights never darken them. |
| `textures_load_on_demand` | Every runtime turns the renderer's missing-texture set into loads (native from disk after presenting, the viewport by asking the editor, web by fetching). A source scan. |
| `background_color_reaches_every_runtime` | Native and web clear to the project's `background_color`, as the editor does. A source scan. |
| `pop_scene_restores_the_live_world` | Every runtime's `push_scene` snapshots the live world before stacking it, and the editor's pop restores that snapshot while keeping the as-loaded one for Stop. A source scan. |
| `persistent_store_is_shared` | Browser `persistent_*` writes reach the engine store and both hosts publish it back. |
| `script_tweens_run_natively` | A Luau script's tweens move position, scale and colour on native, spawn handles included, and cancel. |
| `prefab_package_components_spawn_natively` | A script-spawned prefab's registered components are typed on native at the spawn, and the runner publishes its registry. |
| `sprite_regions_resolve_after_packages` | Every package-hosting runtime (native, viewport, web) resolves atlas regions after the last package phase. |
| `packages_reach_the_web_runtime` | `jengine-web` registers packages before parsing the entry scene, publishes their globals and names before any script compiles, dispatches their commands before its own arms, publishes data tables, runs the six phases at the viewport's points, and has exactly one module-start function whichever crate supplies it. A source scan. |

**None of these catch grade 2.** A behavioural fixture that runs one script
through all four runtimes and diffs the emitted commands is the missing piece.

## 5. The reminder hook

`.claude/hooks/parity-gap-reminder.sh` runs on **Stop** — when a turn ends. If
the working tree touched a parity-critical site and **not** this file, it prints
a one-line notice naming the files.

It cannot detect a gap; nothing can. It notices the *shape* of a change that
often creates or closes one, at the moment you still remember why. It never
blocks, and touching those files without a gap involved is normal — ignore it
then.

Watched: the bridge adapters, `bridge/{command,translator}.rs`,
`scripting/api.rs`, `host_commands.rs`, `core_script_api.rs`,
`lua-runtime.ts`, the viewport and web hosts, and the three ratchet tests.
Edit the pattern in the script to change that.

Disable or review it under `/hooks`.

## 6. Adding a gap

Two lines in the right table beats a perfect entry written later. Include:

- **What** disagrees, named precisely enough to grep for.
- **Which runtimes** — "web" and "the editor" are different answers.
- **Why it is open**, if known. "Needs asset plumbing" and "nobody has done it"
  are both useful; they lead to different next steps.
- **How it was found.** Several of these were found by accident while doing
  something else, and that is worth recording — it says where to look next.

If a fix is one wiring pass, do it instead of filing it. This register is for
gaps with a real reason to stay open.
